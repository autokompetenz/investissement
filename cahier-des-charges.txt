CAHIER DES CHARGES FONCTIONNEL - PLATEFORME D'INVESTISSEMENT
================================================================

1. OBJECTIF DU PROJET
----------------------
Créer une plateforme financière en React JS permettant aux clients de créer un compte, faire vérifier leur identité, investir, augmenter leurs investissements, demander des prêts, demander des cartes bancaires, effectuer des dépôts, consulter leurs opérations et demander des retraits.

L'entreprise et le site étant actuellement en phase de création, l'architecture doit être conçue pour évoluer avec les exigences réglementaires, les prestataires bancaires/paiement et les services crypto utilisés.

Le système doit prévoir deux espaces principaux :
- Espace Client
- Espace Administration


2. FONCTIONNEMENT GLOBAL
------------------------
Client
  -> Création de compte
  -> Vérification du profil/KYC
  -> Validation par l'administration
  -> Activation du compte
  -> Attribution éventuelle d'un IBAN et d'adresses crypto
  -> Dépôt
  -> Investissement / augmentation d'investissement
  -> Demande de prêt
  -> Demande de carte
  -> Suivi du solde et des opérations
  -> Demande de retrait
  -> Vérification et validation par l'administration
  -> Traitement du retrait


3. ESPACE CLIENT
----------------

3.1 Dashboard
Le tableau de bord doit afficher :

- Total investi

- Gains/rendements affichés selon les conditions réelles du produit

- Investir
- Ajouter des fonds
- Augmenter un investissement
- Retirer
- Demander un prêt
- Demander une carte


3.2 Création de compte
Étapes :
1. Email + mot de passe
2. Informations personnelles
3. Adresse
4. Téléphone
5. Informations d'identification
6. Documents nécessaires
7. Soumission du dossier
8. Statut "En attente de vérification"

L'administration peut :
- Valider
- Rejeter
- Demander des informations complémentaires

Statuts :
- PENDING
- VERIFIED
- REJECTED
- SUSPENDED

Le client doit pouvoir consulter/modifier selon les autorisations :
- Nom
- Prénom

- Informations personnelles
- Statut de vérification
- Documents/KYC

4. COMPTES BANCAIRES / IBAN
----------------------------
L'administration doit pouvoir associer un compte bancaire/IBAN à un client.

Informations possibles :
- IBAN
- BIC/SWIFT
- Nom de la banque
- Titulaire
- Devise
- Statut

Côté client :
- Affichage de l'IBAN
- Affichage du BIC
- Bouton "Copier l'IBAN"

IMPORTANT :
Dans une vraie plateforme financière, les IBAN doivent provenir d'un établissement bancaire ou de paiement partenaire autorisé. L'application ne doit pas fabriquer de faux IBAN.

Exemples :

Informations :

- Devise

6. INVESTISSEMENTS
------------------
Le client accède à une page "Investir".

Chaque opportunité peut afficher :
- Nom du produit/projet
- Description
- Montant minimum
- Montant maximum si applicable
- Durée
- Conditions
- Documents
- Risques
- Informations sur le rendement lorsqu'il est applicable
- Statut du produit

Exemple de parcours :
1. Le client choisit une opportunité.
2. Il indique le montant.
3. Il consulte le récapitulatif.
4. Il accepte les conditions.
5. Il confirme la demande.
6. Une opération est créée.
7. Le paiement est effectué.
8. Le paiement est vérifié.
9. L'investissement devient actif lorsque toutes les conditions sont remplies.

Statuts possibles :
- PENDING_PAYMENT
- PAYMENT_REVIEW
- ACTIVE
- MATURED
- CANCELLED


7. AUGMENTATION D'UN INVESTISSEMENT
------------------------------------
Le client doit pouvoir augmenter un investissement existant.

Exemple :
Investissement initial : 5 000 EUR
Ajout : 2 500 EUR
Total : 7 500 EUR

Il est préférable de créer une nouvelle opération "INVESTMENT_TOPUP" liée à l'investissement original plutôt que de modifier simplement l'ancien montant.

Le système doit conserver :
- Montant initial
- Montants ajoutés
- Date de chaque ajout
- Référence de chaque opération
- Total investi
- Statut


8. PAIEMENT D'UN INVESTISSEMENT
--------------------------------
Après confirmation, le client reçoit les instructions de paiement.

Informations possibles :
- Montant à payer
- Devise
- Méthode de paiement
- Coordonnées bancaires ou adresse crypto
- Référence
- Date limite éventuelle

Le client peut signaler :
"J'ai effectué le paiement"

L'administration vérifie ensuite le paiement.

Flux :
En attente de paiement
-> Paiement déclaré
-> Paiement en vérification
-> Paiement vérifié
-> Investissement actif

- Derniers chiffres

17. BACKEND
-----------
Architecture recommandée :

React JS
   |
   v
REST API
   |
   v
Node.js + Express
   |
   v
PostgreSQL / Supabase

Le frontend ne doit jamais être responsable seul des opérations financières sensibles.

Exemple :
Le frontend ne doit pas simplement faire :
balance = balance + 5000

Le serveur doit :
1. Authentifier l'utilisateur
2. Vérifier son autorisation
3. Vérifier le solde
4. Vérifier les règles de l'opération
5. Créer la transaction
6. Mettre à jour les données
7. Enregistrer l'opération dans l'audit
8. Retourner le résultat au frontend

27. CONNEXION DU PORTEFEUILLE TRUST WALLET
------------------------------------------
Les clients pourront associer leur portefeuille crypto à leur compte.

IMPORTANT :
Le site ne doit JAMAIS demander, recevoir, enregistrer ou stocker les 12/24 mots de récupération (seed phrase) du portefeuille.

La connexion doit utiliser une méthode sécurisée de connexion de portefeuille, par exemple WalletConnect ou une solution officielle compatible avec Trust Wallet.

Le système doit récupérer uniquement les informations nécessaires, notamment :
- Adresse publique du portefeuille
- Réseau utilisé
- Type de portefeuille
- Date de connexion
- Preuve/signature de propriété lorsque nécessaire
- Statut de vérification


27.1 PARCOURS CLIENT
--------------------
Le client ouvre :

"Mon portefeuille"

Puis :

[ CONNECTER TRUST WALLET ]

Le système ouvre le processus de connexion du portefeuille.

Le client confirme la connexion depuis Trust Wallet.

Le site récupère alors l'adresse publique du portefeuille.

Exemple :

Réseau :
BNB Smart Chain

Adresse :
0xXXXXXXXXXXXXXXXXXXXXXXXX

Le système peut ensuite demander au portefeuille de signer un message unique afin de vérifier que le client contrôle réellement l'adresse.

Aucune transaction financière ne doit être créée simplement pour vérifier la propriété du portefeuille.

27.6 SÉCURITÉ
-------------
Le système ne doit jamais :
- demander les 12 mots de récupération ;
- demander la clé privée ;
- enregistrer une seed phrase ;
- envoyer une seed phrase au backend ;
- afficher une seed phrase dans l'espace admin ;
- demander au client de transmettre sa clé privée.

La plateforme doit fonctionner uniquement avec des informations publiques du portefeuille et des signatures cryptographiques lorsque nécessaire.

Les opérations financières doivent toujours nécessiter une confirmation explicite dans le portefeuille du client lorsqu'une transaction blockchain est réellement effectuée.


27.7 VÉRIFICATION DE L'ADRESSE
------------------------------
L'administration peut consulter les informations publiques nécessaires :

- Adresse
- Réseau
- Solde public si pertinent
- Transactions publiques si pertinent
- Hash des transactions
- Date de connexion
- Signature de propriété
- Statut du portefeuille

La vérification de l'adresse ne doit pas donner à l'administration le contrôle des fonds du client.


27.8 DÉCONNEXION
---------------
Le client peut demander :

Le système conserve l'historique de l'association précédente, mais marque le portefeuille comme :

Si le client reconnecte un autre portefeuille, une nouvelle demande de vérification peut être créée.

27.10 DIFFÉRENCE ENTRE CONNEXION ET DÉPÔT
-----------------------------------------
La connexion du portefeuille permet uniquement d'associer une adresse au compte et de vérifier que l'utilisateur contrôle cette adresse.

Un dépôt crypto est une opération différente.

Dépôt :
- Le client choisit un montant.
- Le système affiche l'adresse de paiement/dépôt prévue.
- Le client effectue la transaction depuis son portefeuille.
- La blockchain permet de vérifier la transaction.
- Le système enregistre le TxID/hash.
- Le dépôt est confirmé selon les règles définies.

La connexion du portefeuille ne doit donc pas être considérée automatiquement comme un dépôt.
